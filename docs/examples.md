# Examples

Each folder under `examples/` is a complete workflow. This page lists the settings each one needs.

`examples/remediation` takes issues from beads and GitHub to reviewed pull requests. The `round` entry of the project `vars` sets the round. Set `vars.round.merge` to `True` to let the round land approved pull requests through the merge guards. With the default `False`, the owner merges. Set `vars.round.source_checkout` to the absolute path of the checkout of the owner: the implement, review and fix agents cannot write in it, and a git command there that is not a read is refused. Each child run reads its pull request before any agent starts, and the run stops if it is merged, closed, held, a draft, on another base, or its branch is gone. The review loop checks the head before each agent, and it accepts the draft that the run opened itself but stops at any other draft. The batch merge checks the head that the review approved. Set `vars.round.lane_kind` to `papers` or `design` for a lane that changes no source path, and set `vars.round.allow_paths` to the globs it may change: the implement step and each fix step fail when they change any other path. The default `vars.round.lane_kind` is `impl`, which has no path limit. A stop of this kind shows in the result of the run as `stopped`, with the step, the exit code and the reason. The round starts one child run for each ready item and lands the approved heads of a pass with one batch merge: one gate run, the same guards, and a split of the union if the gate is red. An item that stops, or whose head moved since the review, gets its reason as a comment and the hold status, and the other items still land. With `vars.round.merge` set to `False`, the round lands nothing. At the start of each pass, the round merges a moved trunk into the round branch through a sync pull request, with the gate command and a review on the merged head. A conflict that an agent does not resolve, a refusal, a red gate or a review that does not approve stops the round in `round-wait` with its reason (see [the sync step of the round](design/merge.md#the-sync-step-of-the-round)).

`examples/local` needs no tracker and no forge. The items are in `local.db`, and the result is a branch in a git repository on this machine. Copy `examples/local/project.star` to `<config folder>/projects/<name>.star`, set `source`, and run:

```bash
beehave item add <name> fix-login --title "Fix the login" --body-file task.md
beehave run fix-login <name> --workflow examples/local/workflow.star
```

`beehave run` prints a line when the run starts and when each step starts and ends. To see a run later, list the runs, then name one:

```bash
beehave status
beehave status item-fix-login-r1
```

The first command prints one line for each run, starting with the run id. The second prints one line for each step of that run: the name, the start time, the duration, the outcome and the fields that decide the flow. The last line gives the state of the run and, for a failed run, its error. Add `--json` to the second command for one JSON object with the fields `run`, `state`, `error` and `steps`. `beehave run` writes its progress lines to stderr.

`examples/research` answers a question with notes and sources instead of code. It needs no tracker and no forge, and the result is a report file. Set `RESEARCH_TOOLS` to the absolute path of `examples/research/tools` and `RESEARCH_OUT` to the folder for the report.

`examples/incident` is an incident desk. An alert starts a run. An analyst agent proposes one mitigation from a runbook table, and the on-call roles approve it in order, each before a deadline. A safe mitigation runs when someone was paged and nobody answered. A risky one never does. If no page reaches a person, the desk holds the incident. The desk checks the health of the service and restores the earlier state if the check fails. Set `INCIDENT_DIR` to the absolute path of `examples/incident` and `OPS_API` to your ops API.

`examples/research-desk` turns a question into a cited report on a wiki. A planner splits the question into sections, the question run spawns one run for each source, each source run spawns a claims run that reads its page (three levels of runs), and a script tests every quote against the page. A judge agent grades the claims and a person approves the draft before the publish. Set `RESEARCH_DESK_DIR` to the absolute path of the folder, `RESEARCH_HOME` to the folder of the store, `SEARCH_API` to a search server and `WIKI_API` to the page store. The review and the budget pause end with a failed run if nobody answers in time. Run `beehave resume <item>` and then `beehave run` again to continue at the same question.

`examples/ticket-pipeline` loads the support tickets of each day to a warehouse, with an agent that labels the tickets. It covers a backfill of many days in chunks, the retry of one day, a re-run of a range, an idempotent load, a cost budget that waits for a person, and a version change in the middle of a backfill. Set `PIPE_DIR` to the absolute path of the folder and `PIPE_HOME` to the data folder. The folder holds its own README with the engine gaps.

`examples/approvals` is an approval desk. A document needs sign-offs from roles, such as legal, security and product. A person signs each sign-off with an ssh key, and the desk checks the signature. A sign-off binds to one version of the document, and a new version makes the earlier sign-offs stale. The quorum is data: each role has members, a count and a required flag, and `min_roles` sets how many roles must be satisfied. A member can delegate to a person until a time. A run has a deadline, reminders and one extension. Every step is a row in an append-only SQLite ledger, and each row holds the hash of the row before it. `audit.star` checks the chain and the signatures. Set `APPROVALS_DIR` to the absolute path of `examples/approvals` and `NOTIFY_API` to your notifier.

`examples/swarm` runs one backlog with many agents at once. Put one task on each line of the body of the parent item: a priority (`P0` to `P3`), a tab and a title. The parent starts the tasks by priority, no more than the free slots, and lands the pull requests with one `merge` for each priority, `P0` first. A conflict gets a fix run, at most twice, and then a person reads the item. Set `REPO`, `BASE`, `OWNER_LOGIN`, `OWNER_EMAIL` and `SWARM`. Set `agents.max_tree_budget_usd` to cap the spend of the swarm. The folder holds its own README with the engine gaps.

`examples/review-loop` improves one draft with two agents that talk by messages. The author starts the reviewer as a child run and sends it each draft with `send`. The reviewer replies to `"parent"`, and the author waits for the reply with `recv` and a timeout. The loop stops when the reviewer approves, or after three drafts. It needs no tracker, no forge and no settings.

`examples/merge-order` lets two items agree on a merge order. The item that waits runs `waiting.star`: it waits for the message `landed` with `recv`, and merges after it arrives. The dependency runs `dependency.star`: after its own merge, it sends `landed` to `item:<id>` of the waiting item with `send`. Run the waiting item first, and set `WAITER` to its id. Both items are in one project. It needs no tracker, no forge and no settings.

`examples/maintenance` bumps the dependencies of a list of repositories once a week. A scheduler (launchd or cron) starts `scripts/tick.sh`, which skips a repository with nothing new, with the same updates as last week, or with a bump pull request still open, and runs `bump.star` for the others. The workflow updates, runs the gate, lets an agent fix the code for at most two rounds, and opens a draft pull request. If the tests stay red, the run waits for the answer `retry` or `hold`. A weekly report counts every outcome and posts once. Copy the folder to `~/.upkeep`, or set `UPKEEP_HOME`. The README of the folder lists the gaps of the engine.

`examples/queue` runs the open items of a project until no work remains. The parent reads `queue`, starts the ready items in the free slots, and starts the next item when any run ends. A failed item gets a comment and the status `hold`, and the loop goes on after a durable `sleep` of `PAUSE_AFTER_FAILURE` (default `30s`). Set `BASE` to the integration branch, and `OWNER_LOGIN` to your own login: each item reads the forge before its agent starts, and an open pull request by another login holds the item. One login runs one agent step at a time. The pick of a login prefers a login with no agent step running or queued, so the items spread over your logins. The parent run holds no login. With one login, the items run one at a time.
