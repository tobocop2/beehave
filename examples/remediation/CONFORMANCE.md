# Conformance of the remediation example

This file lists the rules of the method and says where `workflow.star` holds each one. It has one row for each row of the parity matrices, so a row can cover several rules. The ID is the first rule ID of the row, or `SC-<n>` when the row has no rule ID. The table has 230 rows. The first sort had 221; the rows that the sort split to give each part its own Home added the other 9. The test does not check the count.

Home says who owns the rule:

- `core`: a general mechanism of the engine.
- `file`: a value or a policy in `workflow.star`, the review loop it loads, or a prompt.
- `skill`: judgment, kept as a skill.
- `drop`: a rule only for a human or AI orchestrator, which the engine does not need.

Status says how far the example goes:

- `gap`: the example does not hold the rule yet.
- `expressed`: `workflow.star` holds the rule and `obee check workflow` passes on it.
- `partly`: a behavior test runs one part of the rule. Where says what the test proves and what it does not.
- `proven`: a behavior test runs the rule.
- `n/a`: the rule does not apply to the engine.

Where is `<file> <builtin> <name>` for an `expressed` row. The file is `workflow.star` or `review_fix.star`, the review loop in the binary. The builtin and the name are those of a call with the keyword `name = "<name>"`. Test names the Go test that checks the row. A `proven` row must name a test. An `expressed` row may leave Test as `-`. When a row names a test, `func <Name>(` must exist in a `*_test.go` file of the repository.

Covers lists every rule ID that the row covers, its own ID first. A row with no rule ID (`SC-`) shows `-`. The Status holds for the Rule text only: in an `expressed` row, the parts of the covered rules that the Rule text leaves out are still gaps.

The review in this workflow is fresh in each round (the `review` agent has no `resume`). The method keeps a conflict open between a resumed reviewer (S1-L-12) and a fresh agent in late rounds (S1-L-19). This example takes the fresh side. An implementer iterating the review to zero, and a reviewer running one sweep, are prose in the prompts and not in the file.

The prompts hold the rules of the brief text that the `brief` package once built from 19 embedded files, in plain words. The test `TestPrompts_HoldEveryRuleOfTheBriefText` keeps one phrase of each rule in the prompts, and fails when a prompt loses one. The rules for the build host, compiled code and a union are in the prompts too. The long-job and handoff-before-launch parts are not in the prompts: the engine submits and waits for each job, so an agent launches none (S1-L-56, drop). The prompts also state rules that the core is meant to enforce. Each of these rules has a row with Home `core` and Status `gap`: S1-P-04 (a reviewer does not fix, commit or push), S1-G-01 and S1-G-11 (gate steps and a result for each step), S1-L-06 (the context cap), and S1-Q-08 (the check for an existing pull request). The four report tables (S1-G-23) are a prompt and an output schema, so that row has Home `file`. The prompts keep the prose until the core enforces it.
